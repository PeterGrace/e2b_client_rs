# M4 Task 9: Cap concurrent uploads in write_files (issue #53)

Plan: `docs/superpowers/plans/2026-10-28-milestone-4-api-stability.md`, Task 9.
Claim: CLM-0176 (S3).

## What changed

- `WriteOptions::max_concurrency(n)` and `DEFAULT_UPLOAD_CONCURRENCY` (8),
  re-exported from the crate root. Octet-stream and gzip uploads run
  through `try_buffer_unordered(n)`: at most `n` in flight, results in
  entry order, and the first error fails the batch and cancels the rest.
  `max_concurrency(0)` is `Error::InvalidArgument` before any request.
- `WriteOptions` has a hand-written `Default`, because a derived one would
  set the cap to 0.
- `docs/protocol-notes.md`: the octet-stream row, and an "At most 8
  octet-stream uploads in flight" bullet under the deliberate differences.
- Tests: 4 in `tests/envd_write.rs` (two count uploads in flight from their
  arrival times, with no wall-clock ceiling), 1 unit test.

## Breaking changes

- A batch of more than 8 octet-stream or gzip files no longer starts every
  upload at once. `max_concurrency(entries.len())` restores the old
  behaviour.

## Divergence from the plan

The plan used `try_buffered(n)`. Its queue is a `FuturesOrdered`, which
yields in input order only, so an error from a later upload waits for every
earlier one to answer: the existing fail-fast test (a 5 s upload first, a
507 second) failed after 5.05 s. The code instead tags each upload with its
index, runs them through `try_buffer_unordered(n)` and stores each result at
its index, which keeps both the order and the fail-fast behaviour. The plan
is corrected in the same PR.

## Why

pgrace chose a default cap of 8 on 2026-10-28 (plan decision 7): a large
batch opened one connection per file.
