# v0.1: REST sandbox lifecycle and envd process and filesystem

- **When:** 2026-10-26T19:42:19Z
- **Issue:** #1

## What changed

First version of the `e2b-client` crate (library `e2b_client`).

- `ConnectionConfig` with a builder and `E2B_API_KEY` / `E2B_API_URL` /
  `E2B_DOMAIN` / `E2B_SANDBOX_URL` resolution in the SDKs' order.
- `Client`: create (`POST /v2/sandboxes`), connect/resume
  (`POST /v2/sandboxes/{id}/connect`, falling back to the v1 route on 404),
  get, list (paged, metadata/state filters), pause, kill, set timeout, refresh.
- `Sandbox` handle with the same lifecycle calls plus `commands()`, `files()`
  and `is_running()`.
- A small Connect-RPC client (`src/envd/connect.rs`): unary JSON calls and
  server-streaming JSON calls with an incremental envelope decoder,
  end-of-stream and error frame handling, and the SDK's plain-HTTP error
  mapping.
- `Commands`: start/run with cwd, env, user, stdin and a stream timeout;
  stream stdout/stderr events to an exit code; connect to a running pid;
  list; send/close stdin; send signal; kill.
- `Filesystem`: read/write over envd's `/files` HTTP API (multipart upload),
  and list, stat, exists, make_dir, rename, remove over Connect.
- `Error` enum (`thiserror`) covering REST, Connect, envd HTTP, protocol,
  timeout and transport failures.
- Tests: unit tests per module, `wiremock` tests for every REST call and every
  envd call (including streaming, end-of-stream and error frames, truncated
  envelopes, timeouts), and `#[ignore]`d integration tests.
- `docs/protocol-notes.md` with file:line citations into the official SDKs
  for every wire fact; `justfile`; GitHub Actions CI; MIT OR Apache-2.0.

## Why these choices

- **JSON Connect, not protobuf.** Both SDKs use Connect's JSON codec for envd,
  so JSON is what servers are known to accept, and it avoids a protoc/prost
  build step. Messages are hand-written serde structs, so no `.proto` files are
  vendored.
- **Response records have public fields.** `SandboxInfo`, `EntryInfo`,
  `CommandResult` and friends are read-only data returned by the server, so
  they expose public fields and are `#[non_exhaustive]` so fields can be added
  later. Request types (`CreateSandboxParams`, `CommandOptions`,
  `ListSandboxesParams`) keep private fields behind builder methods.
- **Non-zero exit codes are data, not errors.** `run` returns the exit code
  instead of raising like the SDKs' `CommandExitException`.
- **No double buffering.** `CommandHandle::next_event` hands chunks to the
  caller; `wait` collects only what remains.
- **The API key never goes to envd.** REST and envd use separate HTTP clients;
  the access token and API key are marked sensitive headers and kept in
  `secrecy` types.
- **Connect v1 fallback.** The test server has no v2 connect route; v1 is
  still part of the E2B OpenAPI spec, so falling back keeps such servers
  working at the cost of one extra request for a missing sandbox.
