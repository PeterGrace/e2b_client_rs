# M4 Task 10: Report symlinks from is_symlink (issue #30)

Plan: `docs/superpowers/plans/2026-10-28-milestone-4-api-stability.md`, Task 10.
Claim: CLM-0177 (S3).

## What changed

- `EntryInfoWire` reads `isSymlink` (also accepted as `is_symlink`), and
  `EntryInfo::from` reports `FileType::Symlink` when it is set, as the SDK
  does (`py: sandbox/filesystem/filesystem.py:130-148`). `list`, `get_info`,
  `rename` and watch-event entries all go through that conversion.
- Tests: the mock test `list_and_stat_report_symlinks_for_both_envd_shapes`
  in `tests/envd_api.rs` (old shape: `type` is `FILE_TYPE_SYMLINK`; new
  shape: `isSymlink` with the target's type), the unit test
  `is_symlink_wins_over_the_reported_type`, and the live test
  `clm_0177_symlinks_report_symlink_type`.
- `docs/protocol-notes.md`: a Filesystem behaviour row for the two shapes.

## Breaking changes

- On newer envd a symlink used to report its target's type (`File` or
  `Directory`); it now reports `Symlink`. Code that relied on following the
  type through a link should read `symlink_target` or stat the target.

## Live result (hosted E2B)

`clm_0177_symlinks_report_symlink_type`: pass on envd 0.10.0 (run
`dev-20261028T142751Z-4137839`).

Hosted envd 0.10.0 uses the new shape. A diagnostic run with the fix
temporarily disabled (run `dev-20261028T142807Z-4141929`, not committed)
failed with `file-link` reported as `File` and `dir-link` as `Directory`, so
the bug was live on hosted E2B and `is_symlink` is what carries the link.
