## Why

**The copy is killed before the snapshot is deleted.** The first run of
`clm_0030` failed at the delete: hosted E2B answers 400 `cannot delete
template '<id>' because there are running sandboxes using it` while a
sandbox made from the snapshot runs. Once the copy is killed the delete
succeeds at once. The snapshot sweep kills the run's sandboxes first for
the same reason, through a helper shared with the sandbox sweep, so the two
sweeps don't depend on the order cargo runs them in. That failed run left
one snapshot; the sweep deleted it.

**Empty values are not sent.** The SDK passes `x if x else UNSET` for the
snapshot name and for every list parameter, so an empty string (and a zero
limit) is left out rather than sent. The crate does the same, and reads a
`null` `names` as empty as the SDK's `list(names) if names else []` does.

**`:` stays unencoded in the delete path.** Both SDKs percent-encode the id
with every reserved character (`quote(value, safe="")`,
`encodeURIComponent`), so they send `:` as `%3A`; the crate's URL builder
encodes `/` (so the id stays one segment) but not `:`, which RFC 3986 allows
in a path segment with the same meaning. Matching the SDK byte for byte
would need a second URL path for one route. Hosted E2B deleted `<id>:<tag>`
snapshots sent this way, and the protocol notes record the difference.

**`SnapshotOptions::mode` cites the SDK's snapshot docs** for the 400 and
409 refusals of a filesystem-only snapshot, and warns that hosted E2B
empties `/tmp` at every boot (found in Task 7), so files meant to survive a
cold boot belong in `/home/user`. `clm_0030` takes a full snapshot, which
restores memory, so its `/tmp` file is kept.
