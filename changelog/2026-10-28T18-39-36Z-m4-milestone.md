## Breaking changes

The list 0.2.0's release notes use. Gathered from the per-task entries
(`changelog/2026-10-28T*-m4-task-*.md`) and checked against the signatures in
`src/` on this branch. Every row is a change from the M3 API (`main` before
PR #101).

### Lifecycle (REST)

| Old | New |
|---|---|
| `client.connect_sandbox(id, None)` | `client.connect_sandbox(id, &ConnectOptions::new())` |
| `client.connect_sandbox(id, Some(t))` | `client.connect_sandbox(id, &ConnectOptions::new().timeout(t))` |
| `client.connect_sandbox_with(id, &o)` | `client.connect_sandbox(id, &o)` |
| `client.pause_sandbox(id)` | `client.pause_sandbox(id, &PauseOptions::new())` |
| `client.pause_sandbox_with(id, &o)` | `client.pause_sandbox(id, &o)` |
| `sandbox.pause()` | `sandbox.pause(&PauseOptions::new())` |
| `sandbox.pause_with(&o)` | `sandbox.pause(&o)` |

`OnTimeout::pause_with(SnapshotMode)` is a different item and stays.

Behaviour, with no signature change:

- Against a server that serves only the v1 connect route,
  `connect_sandbox` returns `Error::SandboxNotFound` where it used to connect
  through `POST /sandboxes/{id}/connect` (Task 1). Without a timeout, connect
  no longer resets the lifetime to 300 s (a v1-only behaviour).
- A pause with a mode (`&PauseOptions::new().mode(..)`) returns
  `Err(Error::Api { status: 409, .. })` for a 409 that does not say "already
  paused", where it returned `Ok(false)` (Task 3). A pause without a mode
  still reads every 409 as `Ok(false)`, as SDK 2.61 does.

### Errors

| Old | New |
|---|---|
| `Error::Transport(reqwest::Error)` | `Error::Transport(TransportError)`; use `TransportError::{is_timeout, is_connect}` or `Error::{is_timeout, is_retryable}` |
| `?` on a `reqwest::Error` into `Error` (`impl From<reqwest::Error> for Error`) | Gone; no reqwest type is public |
| `Error::Api { status, message }` (also `Rpc`, `Envd`) in a pattern | `Error::Api { status, message, .. }`: the three variants are `#[non_exhaustive]` and cannot be built outside the crate |
| `{err}` of `Error::Transport` showed the transport's message | `HTTP transport error`; the detail is `source()` (print the chain, `{:#}` in anyhow) |
| `{err}` of `Error::Decode` was `could not decode response: <serde_json message>` | `could not decode response`; the detail is `source()` |

### Processes and PTY (envd)

| Old | New |
|---|---|
| `commands.connect(pid, Some(d))` | `commands.connect(pid, &CommandConnectOptions::new().timeout(Some(d)))` |
| `commands.connect(pid, None)` | `commands.connect(pid, &CommandConnectOptions::new().timeout(None))`; `&CommandConnectOptions::default()` is 60 s, the SDKs' value |
| `pty.connect(pid, t)` | `pty.connect(pid, &PtyConnectOptions::new().timeout(t))` |
| `PtyOptions::default()` bounded the session to 60 s | No deadline; for the old behaviour, `PtyOptions::default().timeout(Some(DEFAULT_PTY_TIMEOUT))` |
| A `match` on `CommandEvent` or `Signal` listing every variant | Needs a `_` (or `other => ...`) arm: both are `#[non_exhaustive]` |

### Files (envd)

| Old | New |
|---|---|
| `files.read(p, None)` (also `read_to_string`, `read_stream`, `get_info`, `exists`, `make_dir`, `remove`) | `files.read(p, &FileOptions::default())` |
| `files.read(p, Some("root"))` (and the same calls) | `files.read(p, &FileOptions::new().user("root"))` |
| `files.rename(a, b, None)` / `files.rename(a, b, Some("root"))` | `files.rename(a, b, &FileOptions::default())` / `files.rename(a, b, &FileOptions::new().user("root"))` |
| `files.write(p, data, None)` | `files.write(p, data, &WriteOptions::default())` |
| `files.write(p, data, Some("root"))` | `files.write(p, data, &WriteOptions::default().user("root"))`; `write` now honours every `WriteOptions` field (octet-stream, gzip, metadata) |
| `files.list(p, 1, None)` | `files.list(p, &ListOptions::default())` |
| `files.list(p, depth, Some("root"))` | `files.list(p, &ListOptions::new().depth(depth).user("root"))` |

`write_files`, `write_stream` and `watch_dir` keep their shape.

Behaviour, with no signature change:

- A batch of more than 8 octet-stream or gzip files no longer starts every
  upload at once (Task 9); `max_concurrency(entries.len())` restores it.
- On newer envd a symlink reported its target's type (`File` or `Directory`);
  it now reports `FileType::Symlink` (Task 10). Read `symlink_target` or stat
  the target to follow it.

### Timeouts

- `Some(Duration::ZERO)` passed to `CommandOptions::timeout`,
  `PtyOptions::timeout`, `WatchOptions::timeout`,
  `StreamInputOptions::timeout`, `ConnectionConfigBuilder::request_timeout`,
  any `request_timeout` setter, or the `timeout` of `CommandConnectOptions`
  and `PtyConnectOptions` was a deadline that had already passed. It is now
  no limit (Task 4). Code that used zero to fail at once uses
  `Some(Duration::from_millis(1))`.

### Toolchain

- Rust 1.89 or newer (`rust-version = "1.89"`). Builds on older toolchains
  already failed on `uuid@1.29.0`; cargo now names this crate first.

New public items (not breaking): `CommandConnectOptions`,
`PtyConnectOptions`, `FileOptions`, `ListOptions`, `TransportError`,
`DEFAULT_UPLOAD_CONCURRENCY`, the `secrecy` re-export, the classifiers on
`Error`, `request_timeout` setters on the options types,
`WriteOptions::max_concurrency`, and `new()` on `CommandOptions`,
`PtyOptions`, `StreamInputOptions`, `WriteOptions`, `WatchOptions` and
`FileUrlOptions`.

## Follow-ups

- **Volumes on a team that has them.** Re-run `clm_0148`, `clm_0149` and
  `clm_0153_get_info_reports_volume_mounts` where `POST /volumes` is
  enabled; that decides CLM-0148, CLM-0149 and CLM-0153.
- **Per-call request timeouts on REST and pid-only calls.** REST calls and
  `send_stdin`, `kill`, `resize`, `list` and the other pid-only process
  calls use the configured request timeout; only the options-taking envd
  calls have a per-call one.
- **Milestone 5:** the live CI job (CLM-0123) and the publish dry run
  (CLM-0124), then 0.2.0.
- **The live sweeps on sandbawks.** The snapshot and volume sweeps fail with
  404 on their list calls (no such routes, #669, #671), so `just test-live
  sandbawks` and `just test-live-paced sandbawks` can never exit 0, even
  when every test passes. Treating a 404 list as nothing to sweep would fix
  it (PR #115 review).
- **The readiness marker `will not become ready`** also matches an
  unknown-template `action_failure`, so `clm_0150` is labelled
  `FAIL-READINESS (rerun)` on sandbawks although it is #680 (PR #117).
  Until the marker is narrowed, a person reads each `FAIL-READINESS
  (rerun)` line before counting it as capacity
  (`docs/verification/live-pacing.md`).

Not filed (unscheduled, recorded in `docs/protocol-notes.md`, "Not
implemented yet"): the SOCKS5 egress proxy and IAM workload identity, the
volume content API, sandbox health probing, logs, secrets and git.
