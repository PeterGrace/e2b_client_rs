# M2 Task 5: Batch write and the write options

Issue #34, Task 5 of `docs/superpowers/plans/2026-10-27-milestone-2-command-and-file-parity.md`.
Claims CLM-0062 (S3), CLM-0137 and CLM-0138 (S4).

## What changed

- `Filesystem::write_files(&[WriteEntry], &WriteOptions) -> Vec<WriteInfo>`.
  Multipart (the default) sends every file in one `POST /files`, each part
  named `file` with the path as filename, and the `path` query only for a
  single file. Octet-stream sends one `POST /files?path=<p>` per file with
  `Content-Type: application/octet-stream`, concurrently through
  `futures_util::future::try_join_all`. Gzip is the octet-stream request
  with `Content-Encoding: gzip` and a body compressed as it is sent. An
  empty batch returns `[]` without a request.
- `WriteEntry::new(path, data)` and `WriteOptions` with `user`,
  `octet_stream` and `gzip` builders. Gzip implies octet-stream. Both need
  envd 0.5.7 (`EnvdVersion::OCTET_STREAM_UPLOAD`), and older envd gets
  uncompressed multipart, as in the SDKs.
- `write` keeps its v0.1 signature and is now a one-entry `write_files`;
  its wire request is unchanged, and `tests/envd_api.rs` is untouched.
- Shared upload helpers for Tasks 6 and 7: `upload_query`,
  `uses_octet_stream`, `post_octet_stream`, `post_multipart`,
  `written_entries`, `gzip_body`, `no_written_file`, and
  `impl From<UploadedEntry> for WriteInfo`.
- `src/envd/mod.rs`: `EnvdClient::request_timeout()` is back as
  `pub(crate)` (PR #42 had removed it), and
  `http_request_with_timeout(method, path, timeout)` lets uploads choose
  their deadline; `http_request` calls it with the request timeout.
- Dependencies: async-compression 0.4.42 (`tokio`, `gzip`), tokio-util
  0.7.20 (`io`), and futures-util's `alloc` feature.
- Tests: eight mock tests in the new `tests/envd_write.rs`, two unit tests,
  and the live test `clm_0062_write_files_writes_every_file`.
- Docs: an "Uploads" section in `docs/protocol-notes.md`, the "Not
  implemented" line narrowed to streamed uploads, and rows for CLM-0137 and
  CLM-0138 (partial until Task 6) in the S4 evidence map.

## Why it differs from the plan

The plan has been corrected in this same PR:

- tokio's `io-util` feature is not added here, because nothing in Task 5
  uses it (`std::io::Cursor<Bytes>` is `AsyncBufRead` without it). Task 6,
  which needs `BufReader`, now lists `Cargo.toml` and adds it. Dated notes in
  Task 5 Step 1 and Task 6 Step 2, and the file map row.
- `Cargo.lock` pins async-compression 0.4.42, the version the plan's
  verified facts cite; an unpinned resolve picked 0.4.51.
- `upload_query` borrows its values (`Vec<(&'static str, &'a str)>`) instead
  of copying them into `String`s, and `file_query` delegates to it. Fixed
  inline.
- A shared `no_written_file()` error replaces the repeated
  `Error::Protocol("envd reported no written file")` in `write` and in Task
  6's `write_stream`. Fixed inline.
- `write` builds its options with struct-update syntax rather than an
  `if let` and the builder. Fixed inline.
- Task 7 gained a note to carry `UploadedEntry.metadata` through the new
  `From<UploadedEntry> for WriteInfo`.
- The tests are a superset of the plan's: a concurrency test for
  octet-stream and a test of per-file upload errors (507 and an empty
  answer).

The SDK compresses an in-memory gzip upload whole and sends a
`Content-Length`; here it is compressed as it is sent (chunked). Hosted envd
0.10.0 accepted it in a live check (throwaway test, not committed).

## Review follow-ups (PR #45)

- `Cargo.lock` was rebuilt from main's, so it only adds the nine new
  packages. The first version also moved three existing crates from
  windows-sys 0.61.2 to 0.52.0, a side effect of `cargo update --precise`.
- `write_files` documents that octet-stream uploads start all at once with
  no limit, as `asyncio.gather` does, and suggests `entries.chunks(N)` to
  bound a large batch.
- New mock test `octet_stream_batch_fails_fast_without_waiting_for_the_other_uploads`:
  a 507 in a two-file batch is returned before the other, slow upload
  answers.
- `octet_stream_uploads_run_concurrently` now asserts against the
  sequential minimum (3 x 400 ms), not 1 s, which leaves more slack on slow
  runners.
