# M2 Task 8: Signed upload and download URLs

Issue #37, Task 8 of `docs/superpowers/plans/2026-10-27-milestone-2-command-and-file-parity.md`.
Claims CLM-0064 and CLM-0065 (S3), CLM-0140 and CLM-0141 (S4).

## What changed

- `Sandbox::download_url(path, &FileUrlOptions)` and
  `Sandbox::upload_url(path, &FileUrlOptions)` return
  `<envd direct url>/files?path=<p>[&username=<u>]&signature=v1_...[&signature_expiration=<unix s>]`.
  The signature is the SDKs' v1 algorithm: unpadded standard base64 of
  SHA-256 over `<path>:<read|write>:<user or empty>:<token>[:<expiration>]`.
  The query is form-encoded with `url::Url::query_pairs_mut`.
- `FileUrlOptions` (re-exported) has the builders `user` and `expires_in`.
  With no user, envd older than 0.4.0 gets `"user"`, as everywhere else in
  the crate (`EnvdClient::effective_user`). An empty user is left out of the
  URL, as both SDKs do.
- The expiry is the current Unix second plus `expires_in`'s whole seconds,
  as the SDKs compute it. An `expires_in` under one second is
  `Error::InvalidArgument`, because that URL would already be expired
  (from the review of PR #48).
- A sandbox without an envd access token gets the unsigned URL. Asking for
  an expiry on one is `Error::InvalidArgument`, checked before anything
  else, as in both SDKs (2.61.0).
- `EnvdClient` keeps `access_token: Option<SecretString>` next to the
  sensitive header, with a `pub(crate)` accessor. `direct_base` is no longer
  test-only, and `FILES_ROUTE` is `pub(crate)`.
- New dependency: `sha2 0.11.1`. The `Cargo.lock` diff only adds entries
  (`sha2`, `digest 0.11.3`, `block-buffer`, `const-oid`, `crypto-common`,
  `hybrid-array`, `typenum`). `base64` was already a dependency, so its
  `STANDARD_NO_PAD` engine does the encoding.
- Tests:
  - the unit test `file_signature_matches_the_sdk_algorithm` reproduces
    both vectors from the plan;
  - the unit test `signed_urls_carry_the_signature_not_the_token`;
  - the unit test `expiration_is_whole_seconds_and_refuses_under_one_second`;
  - `debug_output_omits_the_api_key_and_access_tokens` now also renders the
    `EnvdClient`, which holds the token itself;
  - four mock tests in `tests/envd_file_urls.rs`, each of which also checks
    the URL does not contain the token;
  - the live tests `clm_0064_upload_url_accepts_a_multipart_post` and
    `clm_0065_download_url_fetches_without_credentials`. Both passed against
    hosted E2B. The second test also showed that the download URL with its
    `signature` pair removed is refused with a 4xx.
- Docs:
  - a "Signed URLs" section in `docs/protocol-notes.md`, with citations
    checked against the 2.61.0 Python and JS packages, and signed URLs
    removed from "Not implemented";
  - CLM-0140 and CLM-0141 rows in the S4 evidence map, and a note on the
    CLM-0122 row.

## Security

The token never reaches the URL, `Debug` output, an error message or a test
log. A `reqwest::Error`'s `Display` includes the request URL, which for a
signed URL is a bearer credential until it expires, so the live tests strip
it with `without_url()` before `expect` can print it. The live logs were
checked for both API keys and for `signature`, and none appear.

## Why it differs from the plan

The plan is corrected in this same PR, with dated notes in Task 8:

- The expiration is `u64`, not `i64`, since Unix seconds after 1970 are
  never negative.
- An empty user is left out of the URL (SDK parity: `if user:`), and a URL
  that does not parse is `Error::InvalidConfig`.
- An expiry under one second is refused, and the expiry is computed in
  whole seconds before adding (review of PR #48).
- The extra token checks in the tests, and the `without_url` stripping in
  the live tests.

Tasks 9 to 11 name none of the changed symbols.
